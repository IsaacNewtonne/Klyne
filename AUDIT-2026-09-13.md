### 1. Executive Summary

**Klyne can become a general-purpose computer agent, but it is not ready to operate as one safely or reliably.** It has useful, connected execution infrastructure—not merely a chat interface—but its permission boundaries, verification contracts, tool interfaces, and recovery behavior differ substantially between execution routes.

The best approach is an **incremental architectural refactor**, retaining the Rust core, SQLite persistence, process supervision, browser integration, and Windows automation work.

The highest-priority change is to make every action pass through the same host-controlled sequence:

**Validate → authorize → journal → execute → observe → verify → reconcile or continue.**

Currently, enabling a broad access switch can grant considerably more authority than the user's particular task requires.

### 3. End-to-End Execution Trace

The primary chat path is:

1. **User submits a message.** `chat.js` posts `/api/chats` with the message, provider, access switches, execution settings, optional workspace, and conversation ID.
2. **The server validates the request.** `main.rs::serve` checks loopback host/origin expectations and request-intent headers. `Chats::send` validates message size, provider settings, active-conversation limits, and pending-action state.
3. **Task state is created or resumed.** A new conversation gets a workspace and SQLite database. Host-workspace selection requires Terminal access. A resumed task cannot replace its acceptance contract.
4. **Success criteria may be created.** A caller can supply a `TaskContract`. Otherwise, `TaskContract::from_goal` recognizes only narrow file-writing language. Ordinary open-ended requests usually have no deterministic contract.
5. **A worker thread starts.** At most four conversations run concurrently. A desktop-enabled turn acquires an exclusive desktop lease before the model loop starts.
6. **The planner is called when no tasks exist.** It returns one to six tasks or a clarification question. Dependencies are validated for unknown references/cycles. Omitted dependencies produce sequential ordering.
7. **A ready task is selected.** Tasks execute serially, even when independent. Worker context includes its assignment and expected result.
8. **The model proposes one action or a state transition.** Decisions include `act`, `verify`, `complete`, `needs_input`, and `fail`. The response is parsed as JSON and checked for required fields.
9. **Model failures receive a bounded correction attempt.** `Chats::request` permits up to two attempts, optionally using a configured fallback provider. Tool execution is not replayed by this response-repair path.
10. **The host dispatches the proposed action.** `Chats::action` branches by tool name. Access checks and error representation differ by branch.
11. **Pending state is saved before execution.** This is a valuable safeguard: interrupted operations can remain unresolved rather than being blindly replayed.
12. **The tool executes.** Shell uses program plus argv, fixed workspace cwd and filtered environment. Desktop performs input and captures an observation. Browser executes CDP then retrieves title/text. API/MCP responses become evidence.
13. **Observation becomes evidence.** Most results are serialized into strings and truncated. Desktop observations retain window/control data and a screenshot.
14. **Some actions receive host verification.** Successful `write_file` calls automatically receive exact read-back checks. Desktop focus/fill and specific document-save paths have additional checks. Other important operations generally depend on model review.
15. **Workers can declare their steps done.** A worker's `complete` marks its task `Done`; this is not independently verified per task.
16. **The reviewer evaluates the overall result.** It may inspect permitted evidence, request repair tasks, ask a question, fail, or complete.
17. **Completion guards run.** Delivery-related keywords cause categorical rejection. Selected action-claim phrases require at least one successful evidence item. A supplied file contract is independently checked. Without a contract, the result is `Reviewed`. Desktop completion additionally requires model output `outcome: "achieved"`.
18. **The final state is saved and shown.** Errors, cancellation, and unresolved actions instead produce blocked/stopped/interrupted states.

Relevant implementation: [chat.rs](apps/studio/src/chat.rs), especially lines 476–727 and 728–1155.

**The core runtime behaves differently:** `AgentRuntime::drive_inner` rejects completion when it cannot obtain a supported file success criterion. Thus, a general conversational or browser objective that Studio can mark reviewed cannot necessarily complete through the core runtime.

Additional observations:

- The host is loopback-bound and has meaningful same-origin defenses. It does not authenticate a local client beyond forgeable headers. This is relevant if malicious local processes are in scope.
- `ProcessJob` controls lifetime; it is not a filesystem/network security sandbox.
- No specific missing-`await` defect was established. Most execution is intentionally synchronous. Primary concurrency risks are lock scope, session sharing, and inconsistent cancellation.
- A separate browser profile isolates cookies/state; it does not itself isolate browser network access or downloaded files from the operating system.

### 7. Recommended Target Architecture

Retain Rust as the host and policy authority. Use independently supervised adapters where mature ecosystems provide clear advantages.

```text
USER / UI / CLI
    │
    ├── Objective, constraints, success criteria
    ├── Scoped grants and approval decisions
    └── Stop / pause / clarification
    ▼
TASK ORCHESTRATOR
    ├── Durable task graph and working state
    ├── Bounded planner / replanner
    ├── Context and artifact selection
    └── Resource budgets
    ▼
CAPABILITY RESOLVER
    ├── Registry schemas and health
    ├── Account / document / application identity
    └── Deterministic route selection
    ▼
HOST PERMISSION BROKER
    ├── Resolve actual target and effects
    ├── Validate existing grant or request approval
    ├── Bind authorization to arguments/version/identity
    └── Enforce filesystem/network/process boundaries
    ▼
ACTION JOURNAL + RESOURCE LEASES
    ▼
EXECUTOR / SUPERVISED ADAPTERS
    ├── Filesystem and documents
    ├── Browser
    ├── Desktop
    ├── Shell and jobs
    ├── Application APIs
    └── MCP / plugins
    ▼
OBSERVATION + ARTIFACT SERVICE
    ▼
VERIFICATION / RECONCILIATION
    ├── Verified → advance
    ├── Known not applied → correct/replan
    ├── Applied, unmet → compensate/repair
    ├── Uncertain → inspect; never blind replay
    └── Human required → checkpoint and pause
    ▼
DURABLE STATE / AUDIT / MEMORY
```

**Route selection should consider authorization before convenience.**

| Task | Preferred route |
|---|---|
| Website operation | Approved documented API → structured browser → accessibility/visual interaction |
| Local data | Filesystem API → format parser/editor → application API → GUI |
| System configuration | Documented OS API → approved command → GUI |
| Desktop application | Application API/automation interface → UIA → keyboard → pixels |

An API using the wrong account is not preferable to a GUI using the correct authorized account. Bind route selection to identity and destination.

**Multi-agent recommendation:** use one orchestrator initially. Optional read-only research or verification workers can help independent work. Separate browser/desktop/terminal “agents” do not inherently improve reliability and introduce coordination overhead.

Allow concurrency only for independent resources. Desktop control, shared browser contexts, and edits to the same document require leases. The permission engine must remain deterministic host code, not a model role with discretion to grant authority.

### 8. Tool Interface Design

The existing `ToolDescriptor` describes names and effects but lacks machine-enforced input/output schemas and operational contracts. The closed `Action` enum also makes arbitrary new tool types difficult.

Use versioned descriptors and validated invocations. This is a **proposed Rust interface**, not an existing Klyne API:

```rust
use serde::{Deserialize, Serialize};
use serde_json::Value;
use std::{future::Future, pin::Pin};

#[derive(Clone, Serialize, Deserialize)]
pub struct ToolDescriptor {
    pub name: String,
    pub version: String,
    pub description: String,
    pub input_schema: Value,
    pub output_schema: Value,
    pub supported_os: Vec<String>,
    pub required_permissions: Vec<String>,
    pub changes_external_state: bool,
    pub confirmation_policy: String,
    pub failure_codes: Vec<String>,
    pub idempotency: String,
    pub supports_cancel: bool,
    pub supports_reconcile: bool,
}

#[derive(Clone, Serialize, Deserialize)]
pub struct Invocation {
    pub task_id: String,
    pub action_id: String,
    pub tool: String,
    pub tool_version: String,
    pub arguments: Value,
    pub expected_state: Value,
    pub deadline_unix_ms: u64,
}

#[derive(Clone, Serialize, Deserialize)]
pub enum EffectState {
    NotApplied,
    Applied,
    Unknown,
}

#[derive(Clone, Serialize, Deserialize)]
pub struct ToolResult {
    pub action_id: String,
    pub effect: EffectState,
    pub output: Value,
    pub artifact_ids: Vec<String>,
    pub error_code: Option<String>,
    pub elapsed_ms: u64,
}

// Created only by the trusted broker, never deserialized from model output.
pub struct AuthorizedCall {
    invocation: Invocation,
    authorization_id: String,
}

pub type ToolFuture<'a> =
    Pin<Box<dyn Future<Output = ToolResult> + Send + 'a>>;

pub trait Tool: Send + Sync {
    fn descriptor(&self) -> &ToolDescriptor;
    fn execute(&self, call: AuthorizedCall) -> ToolFuture<'_>;
}
```

Production requirements:

- Validate schemas before journaling dispatch.
- Derive effective risk from **resolved arguments and current state**, not just descriptor labels.
- Host-trusted policy can override plugin claims.
- Include cancellable execution context and resource leases.
- Pass secret handles, never credential values.
- Return structured data instead of nested JSON strings.
- Preserve error codes and effect state independently of human-readable messages.
- Bind approval to tool digest/version, destination, account, payload and expiry.

For shell operations, return fields such as:

```json
{
  "job_id": "job-123",
  "program": "approved executable",
  "args": ["..."],
  "cwd": "approved workspace",
  "stdout_artifact": "artifact-1",
  "stderr_artifact": "artifact-2",
  "exit_code": 0,
  "elapsed_ms": 842,
  "state": "exited",
  "output_truncated": false
}
```

Exit code zero establishes process success, not completion of the user's task.

### 9. Agent Loop

```text
receive objective
create immutable task identity and scoped constraints
establish acceptance criteria
persist task

while task is active:
    honor cancellation
    enforce remaining time, tokens, money and action budgets

    if unresolved action exists:
        obtain destination evidence
        reconcile without replay
        pause if uncertainty remains

    observe relevant environment
    retrieve bounded working context
    revise short-horizon plan if necessary

    if acceptance criteria appear satisfied:
        independently verify criteria
        if verified:
            persist completion and report evidence
            stop

    choose one next action
    resolve tool, target, account and actual effects
    validate input and preconditions

    evaluate host permissions
    if denied:
        record denial and choose allowed alternative or pause
    if approval required:
        persist exact pending proposal
        wait for user decision
        revalidate target after approval

    acquire resource lease
    persist authorized prepared action
    persist dispatch intent
    execute with cancellation and deadline

    persist returned result and artifact references
    obtain fresh observation
    verify expected result

    if verified:
        advance task state
    else:
        classify failure
        correct, replan, reconcile, compensate or pause

    persist bounded working state and release resource lease
```

Production guidance:

- Use one state machine for CLI and Studio.
- Keep each plan horizon short; do not blindly execute an entire generated graph.
- Make model inference replaceable and side-effect-free from the harness perspective.
- Use schema-constrained output where supported; retain strict host validation regardless.
- Keep `Prepared`, `Dispatched`, `Returned`, `Verified`, and `Uncertain` distinct.
- A crash between dispatch journaling and actual execution remains ambiguous unless the adapter supports idempotency or destination lookup.
- Do not allow the model to set its own acceptance result.
- Propagate cancellation and remaining deadlines through model, tool, observation and verifier calls.
- Track token/cost usage in Studio, not just the number of model/tool operations.
- Reuse provider clients and sessions where appropriate; avoid starting a fresh heavyweight model-agent process for every simple decision.
- Preserve approved user constraints through replanning.

### 10. Security and Permission Architecture

**Risk must be contextual.** Reading a public document differs from reading a credential file; a GET request can still create an external effect.

| Risk | Typical actions | Policy |
|---|---|---|
| Low | Inspect approved public page, list approved directory, observe application | Execute within task grant |
| Medium | Create artifact, edit ordinary workspace file, download data, bounded build | Scoped grant; show diff/target when needed |
| High | Delete, overwrite important data, install software, change settings, publish/send, submit commitment | Explicit authorization covering actual target and payload |
| Privileged | Administrative execution or protected system changes | Separate elevation broker and native user authorization |
| Prohibited route | Bypass authentication, CAPTCHA, UAC/security controls | Stop or request legitimate human completion |

**Approval records** must store:

- User/task identity.
- Action or narrowly scoped action class.
- Canonical destination and account.
- Payload/content digest when relevant.
- Tool version and executable identity.
- Expiry, usage limit and revocation state.
- Whether approval covers retries or compensation.

Changing the recipient, executable, destination, content, or privilege level invalidates an exact-action approval.

**Filesystem boundaries**

- Use explicit read/write roots independent of Terminal.
- Resolve handles and verify file identity; reject reparse escapes and unexpected target changes.
- Keep credentials, harness configuration, policy code and audit stores outside ordinary writable roots.
- Use atomic replacement and preimages for edits.
- Prefer recoverable deletion; permanent deletion requires separate authorization.
- Do not claim cwd or path-string validation contains an arbitrary shell process.

**Process boundaries**

- Use supervised workers with minimal environment and bounded resources.
- On Windows, use Job Objects for lifecycle management, plus an appropriate security boundary for untrusted code.
- Keep privileged execution separate from Studio.
- Never elevate the whole agent to solve one privileged task.
- Run the model interface without independent mutation tools where technically supported; a prompt saying “do not use tools” is insufficient enforcement.

**Secrets**

- User configures a credential connection through trusted UI.
- Store secrets in OS-backed credential storage.
- Expose opaque references bound to origin/account/scopes.
- Inject credentials only inside the approved adapter.
- Never expose a generic “read secret” tool to the model.
- Treat cookies and browser storage as credentials.
- User handles passwords, MFA and CAPTCHA through a paused handoff.
- At-rest storage does not defend against unrestricted same-user code execution; process permissions remain essential.

**Logging and redaction**

- Sanitize before prompt construction and before persistence.
- Cover tool inputs, outputs, errors, URLs, headers, screenshots and recovery incidents.
- Restrict raw diagnostic artifacts with explicit retention.
- Avoid logging entire file contents by default.
- Record model request IDs, usage and latency without storing private reasoning.
- Make redaction failures observable.

**Prompt injection**

Current prompts correctly call external content untrusted, but that is only one layer. Enforce:

1. Provenance tags for every observation.
2. No promotion of webpage/file text into authority.
3. No grant changes from model or tool output.
4. No automatic execution of discovered installation instructions.
5. Destination-bound data-egress controls.
6. Reapproval for consequential scope changes.
7. Adversarial tests across API → shell, browser → filesystem and memory → tool routes.

### 11. Error Recovery Architecture

Use typed failures with explicit effect state.

| Failure | Detection | Recovery |
|---|---|---|
| Invalid model response | Schema validation | One bounded correction; then pause/fallback |
| Missing dependency | Adapter health/preflight | Explain dependency and request installation authorization |
| Stale UI reference | Observation generation, process/window identity | Reobserve and resolve target |
| Covered/disabled control | Actionability/UIA checks | Inspect blocking dialog; choose task-appropriate action |
| Navigation failure | Navigation ID, URL, network/error state | Retry safe navigation or change route |
| Known pre-dispatch network failure | Transport phase | Bounded backoff with jitter |
| Timeout after mutation dispatch | Missing receipt/result | Mark uncertain; query destination |
| Application crash | Process/window event | Restart if permitted, reopen artifact, reconcile saved state |
| Wrong result | Acceptance mismatch | Repair from observed state; preserve previous effect |
| Partial file update | Hash/preimage comparison | Restore or complete atomically |
| Authentication expired | Explicit auth response/UI state | Pause for user authentication |
| Cancellation | Host cancellation signal | Stop dispatch, interrupt owned work, retain uncertainty |
| Repeated no progress | Same state/action/failure fingerprint | Stop retries and request intervention |

Additional rules:

- Do not retry a failed action unchanged solely because a model asks again.
- Track retries per semantic operation, not merely consecutive error messages.
- A successful screenshot should not reset the failure budget for an unchanged failing mutation.
- Before changing API → GUI route, prove the API action was not applied or reconcile its result.
- Compensation is itself an action requiring authorization.
- Exactly-once external execution cannot be guaranteed universally. Use destination idempotency keys or lookup where available; otherwise preserve ambiguity.

The existing `action_journal.rs` receipt approach is worth reusing. Its current messaging tests use a synthetic SQLite destination, not a connected production messaging application.

| Technology | Purpose and fit | Replaces / integration |
|---|---|---|

A large agent framework, vector database, or multi-agent platform is not recommended as a prerequisite. The missing guarantees belong in Klyne's execution architecture.

### 14. Testing Strategy

Separate **deterministic adapter tests** from **model task-success evaluations**.

A mocked model can prove dispatch and recovery behavior. It cannot prove that a real model will identify an unfamiliar control or choose the right tool.

| Scenario | Test and success evidence |
|---|---|
| Create folder and organize files | Seed mixed files; verify destination manifest, hashes and no loss |
| Search online and save results | Controlled search/pages; require source URLs, extracted facts and saved artifact |
| Download and inspect | Serve known binary/document; verify completion, size, hash, MIME and parsed content |
| Edit local document | Change requested paragraph/cell; reopen and verify content plus preservation of unrelated data |
| Run terminal command | Fixture executable emits stdout/stderr and exit code; verify structured output |
| Install harmless dependency | Temporary isolated environment; ensure no installation before approval; verify version afterward |
| Open application and operate | Dedicated fixture app or disposable document; verify process/window identity and resulting state |
| Webpage to spreadsheet | Compare source records against destination cells, types, row count and provenance |
| Failed browser action | Replace DOM after observation; require target refresh and one correct mutation |
| Unexpected popup | Inject modal at action boundary; verify appropriate handling without unsafe dismissal |
| User interruption | Stop during model call, lock wait, process, browser, API and typing; verify no later dispatch |
| Destructive request | Require scoped approval; reject altered path/payload and expired authorization |

**Unit tests**

- Schema validation and unknown-field rejection.
- Permission decisions and grant narrowing.
- Risk resolution from arguments.
- Plan cycles and dependency transitions.
- UTF-8 truncation.
- Redaction and provenance.
- Effect-state transitions.
- Retry/no-progress budgets.
- Approval digest and expiry validation.

**Integration tests**

- Real subprocess streams, stdin blocking, retained pipes and grandchildren.
- Browser tabs, frames, navigation errors, downloads and JavaScript dialogs.
- UIA pattern behavior and inaccessible controls.
- API authentication injection and origin binding.
- SQLite failures, concurrent writes and restart migrations.
- MCP schema/tool-version changes and server disconnects.

**Security tests**

- Junction/symlink swaps between validation and access.
- Shell interpreter requests outside authorized scope.
- Secret forwarding to an unapproved origin.
- Prompt injection in websites, documents, logs, tool descriptions and memory.
- Cross-conversation browser/account contamination.
- Attempted edits to permission code through automatic repair.
- Approval reuse after target/content changes.
- Local HTTP hostile-origin and unauthenticated-client cases.
- Screenshot/log secret leakage.

**Failure injection**

Kill the runtime:

1. Before authorization.
2. After approval.
3. After preparation.
4. Immediately before dispatch.
5. Immediately after external effect.
6. Before response persistence.
7. During verification.
8. During checkpoint commit.

Also inject disk-full, access denied, network reset, lost acknowledgement, expired authentication, application crash and unavailable UIA provider.

**Vision qualification**

Use fixed scenarios across:

- 100%, 125%, 150% and 200% scaling.
- Mixed-DPI monitors and negative virtual-screen coordinates.
- Dark/light themes.
- Moved, resized, minimized and overlapping windows.
- Scrolled/virtualized controls.
- Canvas-only interfaces.
- Dense dialogs and multilingual labels.

Current virtual-screen capture and coordinate offset conversion are useful. They do not establish reliable mixed-DPI or theme-independent understanding. The model receives at most 40 controls from an observation, so paging/querying the accessibility tree is also necessary.

**Release metrics**

Measure:

- Verified task completion rate.
- False-completion rate.
- Unauthorized-action count.
- Duplicate-effect count.
- Recovery success rate.
- Cancellation latency.
- Model/tool latency and token cost.
- Resource leakage over repeated tasks.

Require zero unauthorized or duplicate consequential actions in the release test corpus. Report capability exclusions and skipped live tests explicitly.

### 15. Final Gap Analysis

**1. What can the application do now?**

Klyne can receive a task, generate dependent steps, ask models for actions, execute connected tools, retain evidence, request repairs, pause for clarification, and resume saved work. It can perform bounded text-file operations, supervised commands, basic browser automation, Windows UI interaction, API calls, and curated MCP discovery/invocation.

**2. What does it appear to support but cannot do reliably?**

- Universal completion verification.
- Safe arbitrary terminal use under a single switch.
- General authenticated browser workflows.
- Fully isolated concurrent MCP workflows.
- Browser vision through its native screenshot tool.
- Immediate cancellation across all routes.
- General-purpose automatic recovery.
- Safely qualified self-installed tools and runtime updates.
- Message delivery with production receipts.

**3. What is completely missing?**

A unified action authorization broker, general acceptance framework, full filesystem/document interface, durable interactive job manager, credential/account lifecycle, explicit clipboard tool, comprehensive data-egress controls, and adapter-wide conformance/qualification.

**4. What architectural decisions prevent general-purpose operation?**

- Two orchestration systems with different guarantees.
- Tool routing through names and bespoke branches.
- Permissions organized around transport switches rather than actual effects.
- Verification centered on file criteria and language heuristics.
- State passed primarily as bounded transcript fragments and serialized evidence.
- Shared browser sessions without workflow isolation.
- Safety enforcement inside code the recovery system can modify.

**5. What are the highest-value changes?**

1. Centralize permissions and secret use.
2. Standardize tool results, effect states and cancellation.
3. Unify action journaling and verification.
4. Complete deterministic filesystem, job and browser interfaces.
5. Bind observations and approvals to real resource/account identities.
6. Integrate bounded working memory and evidence retrieval.
7. Qualify extensions and upgrades independently.

**6. What prevents safe arbitrary legitimate computer tasks?**

The system cannot yet reliably constrain broad tools to user intent, distinguish all uncertain effects, verify heterogeneous outcomes, or preserve account/resource identity across routes. Some applications will also require human authentication or expose no dependable automation interface.

**7. What must exist before calling it a general-purpose computer agent?**

A single durable execution architecture with enforced scoped authority, complete reusable primitives, structured observations, evidence-based completion, effect-aware recovery, cancellable jobs, secure credential handling, and demonstrated performance across a diverse task corpus.

**The code is a credible foundation. The next milestone should be a unified, permission-aware execution kernel with verified outcomes—not more hard-coded workflows or additional agent roles.**
