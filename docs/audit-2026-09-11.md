# Klyne capability and reliability audit — 2026-09-11

Klyne is a working, bounded agent prototype with broad optional desktop and process access. It does **not** currently satisfy the requested autonomous, laptop-wide, self-extending harness. Increasing its limits alone would not supply the missing runtime integration, skill discovery, tool activation, app authentication, or recovery.

This audit covers the current dirty working tree, including the untracked Studio implementation, across all eight workspace members. Source, routes, tool dispatch, permission policy, provider adapters, persistence, browser/desktop control, app schemas, experiments, tests, and existing documentation were examined. Existing user changes were preserved. Product code and access settings were not changed. Reproduction helpers and fixtures are under ignored `workspace/`.

“Complete” here means a broad implementation audit against the stated goal, not proof of absence of defects or successful operation of every installed app. Personal apps/accounts were not modified, credentials were not read, and no paid model evaluation was run. This session's Codex sandbox is separate from Klyne's own runtime permissions.

## Capability verdict

| Requested capability | Actual implementation | Gap |
| --- | --- | --- |
| Access laptop files | Typed file tools stay inside each conversation's `files/` directory. Terminal can run interpreters whose arguments access other paths. | No first-class host filesystem roots, directory discovery, or project selection in chat; external work depends on shell/UI. |
| Operate installed apps | Windows screenshots, accessibility, click/type/key/scroll/focus/invoke/fill, and Start-menu app launch. | Shared interactive desktop, no universal app support, no elevation/secure-desktop access, no drag tool, narrow key set. |
| Use app APIs | Persistent local connections, OpenAPI discovery and invocation. | Only numeric loopback HTTP, no credentials/OAuth/header parameters, no LAN/remote service integration or launcher lifecycle. |
| Browse/research | HTTPS fetch in chat; separate CDP browser library. Desktop can operate a visible browser. | CDP is only a Studio dev dependency, not a chat tool. No native search tool. |
| Create/edit skills | Files and scripts can be written; shell could edit external skill files. | No Klyne skill catalog, loader, selector, validation, versioning, or automatic incorporation into subsequent decisions. |
| Create/edit tools | Compiled Rust `Tool` trait/registry; persistent data-driven app operations; scripts executable through Terminal. | No general runtime tool registration, MCP client, plugin loader, or activation protocol. Creating a file does not make it a model-visible tool. |
| Improve itself | Clean Rust repo → isolated worktree → baseline/candidate Cargo tests → retained branch or rollback. | No installation, merge, runtime restart/handoff, or automatic reuse. Current Klyne tree is dirty and does not meet entry conditions. |
| Persist until done | Studio persists snapshots and retains conversation files. Core has richer checkpoints, plans, reconciliation and budget amendments. | Chat uses its own bounded driver, not those core lifecycle facilities. Restart does not resume its workers. |
| Learn from experience | Separate SQLite memory crate with tested retrieval/consolidation. | Studio has no memory dependency/integration; context uses a short history window. |
| Coordinate agents | Planner, workers, reviewer; up to four active conversations. | Worker roles execute sequentially with the same selected provider and shared workspace; no parallel task scheduler or model routing. |

## Priority findings

### P1 — Studio does not use the durable agent loop

Evidence: `apps/studio/src/chat.rs:353` (`drive`), `apps/studio/Cargo.toml`, versus `crates/harness-core/src/agent.rs`.

Studio implements a separate planner/worker/reviewer loop. It snapshots tasks but clears them on follow-up, resets used steps, and replans. An inactive previously running conversation is displayed as Interrupted. If it has pending work, follow-up is rejected and the user must start a new chat. There is no chat reconciliation endpoint, durable scheduler, automatic continuation, or memory retrieval. The root README's core durability features must not be interpreted as Studio chat behavior.

Remedy: make one durable goal executor authoritative for chat, with restartable task state, explicit reconciliation, context retrieval, and continuation. Retain user Stop as a real cancellation signal.

### P1 — Self-extension has no activation stage

Evidence: `apps/studio/src/chat.rs:486`, `apps/studio/src/improvement.rs:7`, `crates/harness-core/src/tools.rs:508` and the Studio dependency list.

Chat recreates a compiled default registry for each standard action, adds Fetch, and dispatches a fixed set of desktop/app/experiment tools separately. No skill loading or general MCP/plugin loading path exists. `self_improve` can produce useful source and tests, but passing results stay on a branch. They do not change the running binary or future prompts. Shell scripts and saved OpenAPI operations provide partial extensibility, not the requested full lifecycle.

Remedy: introduce discoverable capability manifests, skill loading, tool registration, versioned activation and rollback. Binary replacement needs a supervisor capable of checkpointing and handing work to a newly built process.

### P1 — Long conversations can disappear and become inaccessible (reproduced)

Evidence: `apps/studio/src/chat.rs:85` (`save`), `:103` (`get`), and follow-up snapshot query around `:181`.

Save has no matching serialized-size check. Both read paths filter with `length(payload)<4194304`; listing silently drops failed reads. A seeded valid snapshot with 140 messages of 31,000 characters (below the separate 150-message admission threshold) contained 4,347,748 characters. The actual server omitted it from `/api/chats` and returned HTTP 400 `Query returned no rows` on direct access. The small control snapshot returned HTTP 200.

Reproduction: `python workspace/audit_snapshot_probe.py`. This isolates the storage read defect with fixture snapshots; it does not claim 140 such messages were generated by a live model.

Remedy: use separate append-only message/evidence storage and paginated reads. At minimum enforce a compatible save limit and keep oversized historical conversations readable/exportable. A fixed whole-conversation cap undermines long tasks.

### P1 — Shell timeout stops supervising after the direct child exits (reproduced)

Evidence: `crates/harness-core/src/tools.rs:402` joins output readers synchronously after `try_wait` reports exit. Timeout checks exist only in the still-running branch. Reader overflow drains to EOF rather than immediately signalling the supervisor.

A Python parent spawned a child that inherited stdout/stderr and slept for two seconds, then the parent exited. With a 200 ms `ProcessLimits` timeout, the tool returned after approximately 2,070 ms with `ok=true`. A descendant holding the pipe indefinitely can therefore block the tool indefinitely. Studio's between-call deadline/Stop does not interrupt this join. The claim that output overflow immediately terminates the process is also not implemented by the reader.

Reproduction source: `workspace/audit_shell_probe.rs`, compiled against the current harness-core rlib; run `workspace/audit_shell_probe.exe python.exe`. The child sleeps only two seconds and ends itself.

Remedy: supervise direct process exit, descendants, output capture, timeout and cancellation together until all resources have closed; use bounded channels and a process-tree ownership mechanism. Add inherited-pipe and output-overflow regressions.

### P1 — Desktop errors discard uncertain action state

Evidence: `apps/studio/src/chat.rs:544` (`desktop_action` error mapping), `apps/studio/src/desktop.rs:266` timeout branch.

The desktop executor explicitly reports that timed-out input may have an uncertain outcome, but its caller clears `chat.pending` on every error. A click/type may already have happened before observation or screenshot storage fails. A later follow-up is permitted and may repeat the effect without an unresolved-action gate. This differs from crash recovery, which refuses pending actions.

App extension errors are also converted into ordinary failed evidence and their pending markers cleared (`chat.rs:443–478`), even when an HTTP request may already have changed the app. Standard shell timeouts likewise do not prove rollback. This is a recovery-model gap, not a claim that every retry duplicates an effect.

Remedy: distinguish denied-before-dispatch, confirmed failure, confirmed success, and unknown-after-dispatch. Persist full action identity/arguments and require inspection/reconciliation before replay of unknown effects.

### P1 — Local API support excludes many real apps

Evidence: `apps/studio/src/local_apps.rs:13`, `:204`; `apps/studio/src/app_schema.rs`.

Connections accept only `http://127.0.0.1` or `http://[::1]` origins with no path. Authentication, header/cookie parameters, complex serialization, non-JSON uploads and alternate servers are unsupported. There is no readiness/launch/reconnect manager. An installed app, a saved connection and a tested operation are three different states; Klyne only implements portions of that progression.

Remedy: integrate documented launchers and authenticated adapters, including secret references, health checks, schema discovery and verified calls. Expose which route each app supports instead of implying universal compatibility.

### P2 — Hard limits prevent sustained autonomous work

Evidence: `chat.rs:235`, `:315`, `:615`, `connections.rs:31`, plus tool limits below.

Each model decision and tool invocation consumes a shared step; writes also consume independent read-back credit. Consequently 64 steps is materially fewer than 64 productive actions. The guard runs both before and after calls, so reaching the final allowed credit can discard an otherwise valid model result. No chat settings or endpoint expose budget amendments. Invalid JSON and several permission/target errors terminate the turn instead of producing a recoverable observation.

Remedy: configurable persisted policies, renewable execution leases, recoverable tool/model errors, and continuations. Reserve the final verification/summary budget and make the boundary semantics explicit.

### P2 — Shell access is broad but inconvenient for real tools

Evidence: `permissions.rs:373` rejects every executable containing `/`, `\\`, or `:`, even when explicitly granted; `tools.rs:380` clears the environment; `chat.rs:652` never configures environment grants.

The absolute Python executable was rejected in the process probe; `python.exe` resolved through PATH and ran. Apps outside PATH cannot be invoked directly by their absolute executable path through the typed tool. Most inherited environment variables, including user/app/toolchain-specific configuration, are absent. There is no interactive stdin, PTY, configurable cwd or durable process handle. Shell interpreters can work around some limitations, but the runtime provides no supported first-class interface for them.

Remedy: validate canonical executable identities, explicit host project/cwd selection, environment profiles and asynchronous process sessions. Keep controls observable and user-configurable.

### P2 — Stop is not end-to-end cancellation

Evidence: `chat.rs:615`, synchronous `connections.rs:31` and `:336`, `main.rs:487` serial accept loop.

Chat generally checks Stop between calls. Provider calls may take 120 seconds; normal shell/fetch calls nominally 30 seconds; local APIs 20 seconds. Self-improvement suites poll cancellation, but Git operations do not. HTTP management routes can themselves perform synchronous discovery/provider checks/desktop operations while occupying the one server handler, delaying the Stop request.

Remedy: propagate cancellation/deadlines into all providers and tools; handle HTTP requests concurrently with a small bounded pool; keep Stop/status responsive under slow clients and app calls.

### P2 — No process-wide ownership of Studio state or desktop across servers

Evidence: `main.rs:452`, `chat.rs:74`, `desktop.rs:142`.

Active conversations and the desktop lease live in process-local memory. Two servers on different ports can open the same root, and separate server processes can each think they own the desktop. SQLite transactions protect individual snapshots but not the entire task lifecycle.

Remedy: acquire a root ownership lock and machine/session-wide desktop lease. Reject conflicting owners before accepting actions.

### P2 — Completion evidence is uneven

Evidence: `chat.rs:398–418` trusts the reviewer completion decision; `:509` independently checks new whole-file writes; `local_apps.rs:40` denies reviewer calls.

Independent content read-back is useful, but there is no required structured success criterion for arbitrary chat goals. The same selected model is used for planning, work and review. Reviewers cannot run tests or query live app APIs, so they often cannot independently validate external outcomes. Shell/app/desktop success mostly means the tool call returned, not the requested user outcome was achieved.

Remedy: task-specific verification contracts, read-only test/inspection facilities, and explicit unverified outcomes when independent evidence is unavailable.

### P2 — Self-improvement gates are limited and current repo is ineligible

Evidence: `crates/harness-experiment/src/lib.rs:339`, `:373`, `:392`; `apps/studio/src/improvement.rs:49`.

The runner rejects dirty repos. The audited workspace already contained numerous modified tracked files and untracked Studio sources. It cannot directly self-improve through this route without an isolated clean snapshot. The fixed suite is `cargo test --offline`; absent dependencies, non-Rust projects and slow builds are outside this route. Passed-test counts do not prove preserved test identities or behavior; candidates can edit implementation and tests together. Test processes execute with host authority, so filesystem worktrees do not roll back arbitrary external test side effects.

Remedy: preserve user work in an isolated committed candidate snapshot, use project-specific independent gates and protected regression expectations, and treat activation/rollback as separate operations. Do not reset or silently commit the user's working tree to satisfy this precondition.

### P2 — Core delegation budget is not an atomic parent-owned pool

Evidence: `crates/harness-core/src/delegation.rs:70` accepts parent-used/limit numbers and checks subtraction; it does not reserve credits in a shared parent store.

Multiple callers can each reuse the same remaining-budget snapshot. Resource inheritance and accounting require coordination by the caller. This is a core-library gap; Studio does not currently call this delegation function.

### P2 — CDP transport still has documented hardening gaps

Evidence: `crates/harness-browser/src/cdp.rs:11`, `:151`; `ws.rs:1`.

HTTP headers/body are not explicitly size-capped; missing/invalid Content-Length defaults to zero. Future response IDs are parked and can later return before their request is sent. Events can be dropped while waiting for command responses. WebSocket Accept is not verified, and debugger URLs are not strictly validated as loopback at the split function. Passing controlled Chrome tests does not exercise hostile or malformed debugger peers.

Remedy: strict framing, total deadlines, bounded events/responses, handshake verification and target validation before making this a general chat browser backend.

### P2 — Broad access toggles are not OS isolation

Evidence: `chat.rs:663` grants the model-selected program whenever Terminal is on; desktop instructions explicitly permit visible terminals/browsers independently of other switches.

Terminal already gives broad process authority under the Studio Windows user. Desktop can operate apps that themselves access files/network. Web off does not mean the agent cannot reach the network through another enabled route. Filesystem path checks do not defend against every hostile concurrent replacement/hard-link scenario. This is relevant to accurate access expectations, not a recommendation to prevent the requested laptop access.

Remedy: show effective authority clearly. Offer an explicit trusted-laptop profile with configurable roots, tools, apps and execution policy; retain an immediate Stop and durable action ledger.

### P3 — Documentation overstates or inconsistently describes integration

The README still calls general planners planned while Studio has a planner. `docs/resource-limits.md` calls some features planned that newer core files implement. Older audits contain now-superseded desktop/lifecycle descriptions. Tests use controlled providers; a test named `real_model_repairs_controlled_repo_through_runtime_boundaries` is not by itself evidence of current real-model general intelligence. Record coverage by product surface and distinguish source implementation, fixture validation and live task performance.

## Effective limits inventory

| Surface | Current bound |
| --- | --- |
| Chat instruction | 8,192 bytes; HTTP body 16 KiB |
| Chat turn | 64 shared model/tool steps; 900 seconds checked between calls |
| Planning/review | 1–6 sequential tasks; at most 3 review passes |
| Context | Latest 18 messages, latest 6 observations, original goal, tasks; 128 KiB prompt cap |
| Model output | 32 KiB chat response |
| Persistence | Read query below 4,194,304 characters; no matching write bound |
| Conversation admission/list | Reject follow-up above 150 messages or evidence entries; list newest 100 |
| Concurrency | Four chat conversations per server; desktop lease one per process |
| Standard file tools | Whole read/write/range 1 MiB; stream/hash/patch file bound 64 MiB |
| Shell | 30 seconds nominal; 64 KiB per stream; closed stdin; workspace cwd |
| Model calls | 120 seconds; new ephemeral Codex process or new OpenCode session per decision |
| Local APIs | 64 connections; up to 256 discovered operations; one operation per result page |
| Local API transport | 20 seconds; 32 KiB body; 64 KiB response; 1 MiB schema fetch |
| Desktop | 20-second helper; 4 MiB screenshot; 4,000-character input; 180-second observation validity |
| Self-improvement | Clean Rust repo; 1–16 files, 1 MiB contents, further constrained by 32 KiB model output; 300 seconds per suite |

Removing every numerical bound would not make this reliable: streaming, background jobs, pagination and renewable work are needed to handle genuinely large tasks without truncation or hangs.

## Verification evidence

- Full workspace test log reports **179 passed, zero failed**, plus successful doc-test targets, after the approved outside-sandbox rerun. All eight controlled browser tests and Studio browser integration flows passed. Initial sandbox run failed seven Chrome tests with Windows error 10054; those failures did not reproduce outside the sandbox.
- Log: `workspace/audit-2026-09-11-tests.log`. Windows PowerShell's native stderr redirection produced a `NativeCommandError` wrapper and tool exit code 1 despite every Cargo test target reporting success. This is a wrapper caveat; the audit does not silently label that shell invocation exit-zero.
- `cargo clippy --workspace --all-targets --all-features --locked --offline -- -D warnings`: passed, exit 0.
- `cargo fmt --all -- --check`, both frontend `node --check` commands, and `git diff --check`: no check errors (Git emitted line-ending warnings).
- File benchmark: 10/10 positive tasks independently verified and 10/10 traversal cases denied; 30 tool calls, approximately 0.515 seconds.
- Large-file benchmark: 8 MiB file, independently verified, three tool calls, approximately 0.497 seconds.
- Snapshot and inherited-output-pipe probes reproduced the defects above with isolated fixtures. They are not included in the 179 existing tests.
- Python, Rust/Cargo, Node, Git, Codex, Ollama and OpenCode executables were discoverable on this laptop. That establishes availability on PATH, not successful authentication, server readiness or arbitrary app compatibility.
- Live desktop typing/clicking in personal apps, authenticated app integrations, paid model task quality, crash recovery across runtime upgrades, long-duration operation and adversarial isolation remain unverified. Existing desktop tests mostly cover parsing, denial and invalid launch targets, not an end-to-end real-app task.

## Implementation order to reach the intended harness

1. Fix persistence sizing, unknown outcomes, subprocess supervision, and root/desktop ownership. Add regressions for the concrete failures, then make Stop reliably interrupt every execution path.
2. Integrate Studio with durable goals, memory retrieval, resumable task state and configurable continuing execution. Add host-project selection and persistent process sessions.
3. Add skill discovery/loading and a dynamic tool/MCP interface with versioned manifests. Prove that a newly created skill/tool is discovered and successfully used in the next turn and after restart.
4. Add app readiness/launch management, authentication and reusable adapters; connect the CDP browser backend. Prove tasks against representative real apps with independent read-back.
5. Complete improvement activation: clean isolated snapshot, independent tests, retained rollback version, supervisor handoff, and recovery of the active goal after upgrade.
6. Benchmark real requested tasks: multi-hour coding, app workflow completion, new skill acquisition, creation and reuse of a new tool, and restart during external actions. Report completion rate, interventions, duplicate effects, latency and actual model usage.

The largest missing piece is the path from a model identifying a needed capability to creating it, validating it, loading it, and continuing the original goal durably. Broad Terminal access already supplies much of the raw laptop authority; that lifecycle is what turns it into the powerful harness described in the request.
