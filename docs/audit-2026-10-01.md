# Instruction reliability audit — 2026-10-01

## Verdict

Klyne has working tool execution, persistence, permissions, and verification infrastructure, but it is not yet a reliable general-purpose assistant. Passing deterministic fixtures does not establish that a live model will follow a natural-language instruction, finish efficiently, or satisfy subjective quality requirements.

This audit preserved the checkout's existing staged and unstaged changes. It combined repository-wide regression checks, focused source review of the instruction lifecycle, read-only inspection of the user's saved failures, and isolated live tests of the installed Ollama model. The user's album and saved conversations were not modified. This is an engineering audit, not a proof of every possible behavior or a dependency-advisory assessment.

## Real failure history

The saved album conversations show distinct problems:

- `1790784166877-0` and `1790785026829-0`: HTTP 404 from the model server before any task execution. The historical error omitted the server's explanation, so it cannot establish whether the model name or route was missing. The selected Qwythos model is absent from the currently returned installed-model list.
- `1790785526888-0`: the model tried `read_file` on an absolute album directory while the conversation still used its private default workspace. Path policy denied the operation; the model then failed to justify its clarification request.
- `1790786798251-0`: the selected workspace was the album, but the model planned to ask for creative constraints instead of inspecting the supplied material. It invented an ethical/legal prerequisite for the request and stopped without tool evidence.

The working tree already contained project-path inference, directory-read conversion, model selection UI, and task-specific text-revision prompting before this audit. Those changes must not be mistaken for fixes newly authored here. Existing path regression tests were included in validation.

## Remaining release blockers and limits

1. **Quality review is not independently calibrated.** The same selected model performs planning, work, and review. A separate role is not a separate source of competence. The live lyric example demonstrates a false-positive quality review. Test real task requirements with human-reviewed examples before claiming creative or general task reliability.
2. **General task-success coverage is small.** Three local file cases cannot establish arbitrary application automation, authenticated services, installations, full-album editing, or long coding tasks. Extend the live corpus using user-reported failures and grade actual outcomes, completion time, duplicate actions, and unnecessary questions.
3. **The live model still loops on simple multi-output work.** Retaining receipts and correcting contradictory instructions did not resolve the two-file repeat. This remains a measured release blocker, not just a hypothetical risk.
4. **Context retention is bounded.** The model sees a limited message/evidence window and can retrieve historical evidence. Long tasks still depend on selecting relevant context; receipts are not a complete semantic memory of every requirement.
5. **Desktop access is reserved at conversation admission.** Enabling Desktop causes a worker to wait for the shared desktop lease even for file-only tasks; it can block after 30 seconds of contention. Lazy acquisition would require careful lifetime and cancellation changes and was not implemented here.
6. **Final persistence errors can be hidden.** The worker's final `save` result is discarded before its active entry is removed. Disk-full or I/O failure could leave persisted status behind the actual worker. No disk-full fault injection was performed.
7. **Effect guarantees have boundaries.** Shell and DELETE approvals are host enforced; arbitrary semantic consequences of desktop clicks, scripts, and API calls are not universally classified. Process lifetime management is not OS sandboxing. Destination observations remain model-reviewed unless backed by a supported host acceptance check.
8. **Environment coverage is bounded.** Windows local checks do not validate hosted Linux CI, every browser/site, multi-monitor/DPI behavior, live Codex/OpenCode behavior, or dependency advisories. Those are not counted as passes.

## Coverage

- Input and UI: settings persistence/isolation, submitted workspace, activity state, mobile layout, and public demo through existing browser suites.
- Planning and execution: new/resumed goals, dependency ordering, budgets, approvals, schema recovery, file tools, repair loops, and completion paths through source review and Rust fixtures.
- Providers: current Ollama installed-model discovery and live execution; mocked provider protocol, cancellation, retries, and usage checks. No paid/cloud inference was invoked.
- Persistence/recovery: SQLite and action journal review; crash, restart, reconciliation, process-tree, protected experiment, and recovery-service tests.
- Access: existing traversal, origin, secret-binding, review-only, and approval tests; local HTTP request checks reviewed in source.
- Desktop/browser: controlled browser suite and dedicated Windows desktop recovery fixture; arbitrary real applications remain outside the measured corpus.
- Delivery: fresh-launch build check, formatting, Clippy, regression workflows, and release/test-tier documentation reviewed.
